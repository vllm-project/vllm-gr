# 多 Batch 功能进展

截至 2026 年 10 月，[上游 PR #433](https://github.com/JiusiServe/vllm-gr/pull/433) 已合入 GPU Beam 多 Batch 能力，支持一次处理 1、2 或 4 个请求，并按输入顺序返回结果。请求结束、取消及资源释放也已纳入 Batch 流程。

目前，离线单进程场景的框架开销已降至约 **4 ms**，这部分优化已比较充分。GPU 和 NPU 在 EngineCore 及以上共用调度与请求流程；到 Worker 层分别实现各自的设备执行逻辑，保持对外功能一致。

## GPU 测试结果

PR #433 使用 OneRec-1.7B、输入长度 1024、Beam 宽度 128、生成 3 个 SID token、CUDA Graph；预热 2 次，测量 5 次。下表为 PR 中的耗时数据：

| Batch 大小 | 串行执行 B=1 | Batch 执行 | 平均每请求 | 相对串行加速 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 55.10 ms | 54.97 ms | 54.97 ms | 1.002× |
| 2 | 109.83 ms | 94.31 ms | 47.15 ms | 1.165× |
| 4 | 221.83 ms | 177.62 ms | 44.40 ms | 1.249× |

B=4 时，平均每请求耗时比单独执行 B=1 低约 19%。这里的耗时是完整请求耗时，与上面的约 4 ms 框架开销不是同一个统计口径。

输出一致性还需继续复核：PR 原始测试中，B=2 和 B=4 的 Top-1 均与单请求结果一致；后续使用替代约束表的复测观察到部分 Top-1 差异。后续应使用真实约束表确认这一结果。

## 后续

在 GPU、NPU 功能逐步对齐后，考虑重构 Worker 侧的重复逻辑，继续保持上层共用、设备侧独立的边界。
